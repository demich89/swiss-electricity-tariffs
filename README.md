# Swiss Electricity Tariffs

A lightweight, independent electricity tariff website and public JSON API. Built for GitHub Pages with plain HTML, CSS and JavaScript, a Node.js collector, and no runtime dependencies.

**Currently supported:** AMB (Azienda Multiservizi Bellinzona), dynamic high/low tariff schedules. The provider registry and selector support adding further verified Swiss providers. Nationwide coverage, monetary rates and arbitrary dynamic price bands are not implemented.

## Features

- Current tariff with the time it ends and the time remaining, plus the next confirmed change.
- Today's and tomorrow's schedules as a proportional day timeline and as labelled low, high and unknown blocks, with the current block highlighted.
- Europe/Zurich time, including 23-hour and 25-hour DST days. The UTC offset is shown once per day, and on every time on DST days.
- Shareable links: `?provider=<id>` opens that provider; unknown IDs fall back to the default.
- Fetch timestamps, stale-data warnings and strict interval expiry.
- English by default, with German, French and Italian translations sourced from English.
- Versioned provider discovery and tariff endpoints with per-provider collection status, generated by scheduled GitHub Actions. The API page lists providers from the live catalog and builds endpoint, curl and JavaScript examples for the selected one.

This is not an official provider website. It contains no Home Assistant integration, consumption tracking, solar calculations or bill estimates. Existing Hass.io repositories are outside its scope.

## Run locally

Requirements: **Node.js 22+** and **Python 3**. No dependency installation or build step is needed.

```sh
npm test
npm run fetch
npm start
```

Open **http://localhost:8080** and **http://localhost:8080/api/** for API documentation. Stop the server with Ctrl+C. If port 8080 is busy:

```sh
python3 -m http.server 8081 --directory public
```

`npm run fetch` contacts the upstream providers and rewrites generated JSON. Tests use fixtures and synthetic adapters, never live requests. Checked-in snapshots allow an initial local preview but may be stale; their timestamps are never refreshed without a successful collection. Serve over HTTP rather than opening HTML through `file://`.

## GitHub Pages setup

1. Push to GitHub using `main` as the default branch, or update both workflows for your branch name.
2. In **Settings → Pages → Build and deployment**, choose **GitHub Actions**.
3. Enable Actions and run **Collect tariffs and deploy Pages** from the Actions tab, or push to `main`.
4. Find the published URL in the deployment result or Pages settings.

No secrets, server or database are required. Relative URLs support repository project paths as well as root domains. The deployment job uses the `github-pages` environment; configure protection rules there if needed.

The workflow runs hourly at minute 17, on pushes to `main`, and manually. Scheduled Actions can be delayed, dropped or disabled for inactive repositories. The schedule is not a freshness guarantee. Collection and deployment have a 15-minute build timeout; collection retries each request up to three times with a 30-second request timeout.

Providers collect independently. After an upstream failure, the collector can carry forward that provider's validated snapshot from the currently deployed Pages site, preserving its original `fetchedAt` and `staleAfter`. It never falls back to checked-in data. New failed providers with no deployed copy are omitted from discovery. An unavailable default provider or a run with no fresh provider collections blocks publication; the previous deployment stays available. The catalog records collection status and timestamps so reused data cannot look newly fetched.

The workflow passes the deployed URL through `PREVIOUS_SITE_URL`, configured from the Pages action. Local runs have no fallback unless you explicitly set that variable to the trusted deployed site base URL, including its trailing slash. The first deployment likewise has no earlier site to reuse.

For partial failures, valid outputs publish first; a separate reporting job then fails the overall workflow so upstream outages remain visible in Actions. Configure GitHub notification preferences to receive workflow failure notifications. A dedicated alert service and public status dashboard are not implemented. Watch catalog freshness as well: a failed workflow that cannot deploy leaves the previous catalog unchanged.

## Data rules

Each interval has a UTC Unix-millisecond `start`, an exclusive `end`, and a `low` or `high` tariff code. Intervals must be sorted, non-overlapping and valid for at most 15 minutes. Gaps are always unknown. There is no assumption of exactly 96 readings per day.

The AMB adapter requests four UTC days, from the day before the current Zurich calendar day through two days after it. This covers today and tomorrow across DST boundaries. It checks equal array lengths, UTC timestamps and exact known colors. Identical duplicate timestamps merge; conflicting duplicates fail collection. An interval ends at the next timestamp or after 15 minutes, whichever comes first. Individual empty daily responses may leave gaps; an entirely empty result fails collection.

The browser computes status from the device clock every 30 seconds and reloads the catalog and snapshot every five minutes while the tab is visible, and immediately when it becomes visible again. Fetches time out after 15 seconds. Provider changes clear the previous provider's data, and late responses cannot overwrite a newer selection. A failed refresh retains any valid data already loaded for the same provider, with a warning. When the catalog marks a provider `stale`, the page says the provider could not be refreshed and names the fetch time of the schedule shown.

AMB's snapshot `staleAfter` is six hours after its successful fetch. The browser uses this snapshot timestamp as the freshness source of truth, rather than recomputing it from catalog settings. A catalog entry with `status: stale` also triggers a fetch-failure warning even if its snapshot is younger than six hours. Stale data can still contain future intervals; the website shows them with a warning, but never extends an expired interval. Future fetch timestamps more than five minutes ahead also trigger a warning. The next change is shown only within continuous known coverage. Source completeness is not guaranteed: missing coverage is visible as unknown.

## Public API

```text
GET api/v1/providers.json
GET api/v1/providers/amb/tariffs.json
GET api/v1/tariffs.json                  # AMB alias, retained
```

```sh
curl --fail http://localhost:8080/api/v1/providers.json
curl --fail http://localhost:8080/api/v1/providers/amb/tariffs.json
```

There is no API key. Resolve a catalog entry's `tariffsUrl` relative to the catalog URL, including the repository prefix. API field names and labels are English and do not change with website language. The original Dutch display labels have been replaced by English labels; machine codes `low` and `high` remain unchanged. Clients should use codes rather than labels for logic.

See [the API contract](docs/api.md) and the locally served `/api/` page for fields, examples, caching and limitations. No additional licence to provider source data is implied.

## Add a provider

Run `npm run new-provider -- <id>` and follow the printed steps; see [the provider guide](docs/adding-providers.md). A provider is an adapter plus registry metadata, tests and verified source documentation. A new supported high/low provider automatically appears in the website selector and discovery API after collection. Do not add placeholders or represent missing data as low tariff.

## Languages and contributions

English is the source language for code, documentation, fallback HTML and API labels. Update `public/locales/en.js` and `public/api/locales/en.js` first, then translate the same keys into `de.js`, `fr.js` and `it.js`. Documentation and website dictionaries use separate namespaces. JSON examples and API codes stay language-independent.

The choice is saved as `electricity-language` in localStorage. Unsupported choices fall back to English; blocked storage does not prevent switching. Language changes never change the timezone. Tests check key parity and static HTML coverage.

Before submitting a change, run `npm test`. For collector changes, add captured or synthetic response fixtures and test source failures and missing coverage. Use live `npm run fetch` separately to verify upstream compatibility. Keep generated snapshots consistent when committing them; the deployment workflow always fetches fresh data and does not commit it back.
